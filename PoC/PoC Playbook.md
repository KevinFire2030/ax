# PoC Playbook (메일 기술자료 리스크 탐지/차단)

이 문서는 오늘 구현한 **4가지 PoC 데모**를 프로젝트 참여자(비개발자 포함)가 쉽게 이해하고 직접 실행/시연할 수 있도록 정리한 플레이북입니다.

> 핵심 한 줄
> - **사후 탐지(post-detection)**: 이미 발신/수신된 메일 이력을 내려받아 분석
> - **사전 차단(prevention)**: 메일 전송 직전에 분석해 Allow/Warn/Block로 분기

---

## 0) 전체 그림 (왜 4개인가?)

우리는 같은 목적(기술자료 수발신 위험 탐지)을 2개 축으로 나눠 PoC를 구성했습니다.

1) **언제 검사하나?**
- 사후 탐지: 메일을 보낸 후(이력 Excel 기반)
- 사전 차단: 메일을 보내기 전(전송 직전 검사)

2) **어떻게 검사하나?**
- 키워드 기반: 특정 단어/확장자 포함 여부(빠르고 단순)
- 문맥 기반: LLM이 요청 의도/기술자료성/근거를 판단(정교)

따라서 데모는 아래 4종입니다.

| 구분 | 방식 | 목적 | 한 줄 요약 |
|---|---|---|---|
| PoC-1 | 사후 + 키워드 | 빠른 1차 선별 | 키워드/확장자로 걸러서 검토 후보 만들기 |
| PoC-2 | 사후 + 문맥(LLM) | 키워드 한계 극복 | 후보(또는 일부)에 LLM을 태워 리스크 등급+근거 생성 |
| PoC-3 | 사전 + 외부 훅(서버) | 실감 나는 차단 UX | 전송 직전 외부 에이전트가 검사해 Allow/Warn/Block 팝업 |
| PoC-4 | 사전 + 내부 호출 | CPCex 내장형 모델 | CPCex 내부가 직접 LLM 호출해 Allow/Warn/Block 분기 |

---

## 1) PoC-1: 사후 탐지 / 키워드 기반 (Keyword-based post-detection)

### 무엇을 보여주나?
- 메일 이력 Excel을 읽어 **제목/본문/첨부파일명**에서 키워드를 찾고
- 탐지된 키워드를 컬럼에 기록해 **검토 우선순위용 결과 파일**을 만든다.

### 누가 보면 좋은가?
- 담당자(실무자): 후보 메일 리스트를 빠르게 뽑아 검토량 줄이기
- PM/임원: “현행 키워드 선별”이 어떤 출력물을 만드는지 확인

### 입력/출력
- 입력: `sample_data_raw.xlsx` 같은 메일 이력 Excel
- 키워드 파일: `detection_keywords.md` (한 줄에 키워드 1개)
- 출력: `keyword_based_detection_by_dept.xlsx`
  - Sheet1: 전체
  - 부서별 시트: 히트된 행만

### 실행(개발자)
- 폴더: `E:\ax\상생\PoC\사후 탐지(post-detection)\keyword-based`
- 자세한 실행은 해당 폴더의 README 참고

## 2) PoC-2: 사후 탐지 / 문맥 기반 (Context-based post-detection)

### 무엇을 보여주나?
- 전수 데이터를 한 번에 LLM에 태우는 대신,
  1) 전수에서 **후보군을 만들고**
  2) 후보에만 LLM을 태워
- 메일별 **리스크 레벨(0~5)**, **점수(0~100)**, **근거(evidence)**를 만든다.

### 왜 중요한가?
- 키워드가 없는 우회 표현(예: “구조 검토 요청”, “sample data review”)도
  **문맥으로 탐지**할 수 있음을 보여준다.

### 입력/출력
- 입력: 메일 이력 Excel
- 프롬프트: `prompt_context_detection.md`
- 설정: `.env` (후보비율/히트 기준/병렬 수/캐시 등)
- 출력: `context_based_detection_by_dept_YYYYMMDD_HHMMSS.xlsx`

### 실행(개발자)
- 폴더: `E:\ax\상생\PoC\사후 탐지(post-detection)\context-based`
- 자세한 실행은 해당 폴더의 README 참고

## 3) PoC-3: 사전 차단 / 외부 훅(에이전트 서버) 방식 (Prevention via webhook)

### 무엇을 보여주나?
- “메일 전송 화면”에서 **전송 버튼을 누르는 순간**
- 외부 검사 서버가 LLM으로 문맥 판정하고
- 결과에 따라 UI가 갈라진다.

정책
- Allow: 자동 전송
- Warn: 경고 팝업(사유/근거) + 전송은 허용(override 로그)
- Block: 전송 불가 + 승인(3단계 라우팅) 필요

### 구성요소
- 에이전트 서버: `detection_agent_webhook.py` (FastAPI)
- UI 페이지: `/ui` (한 페이지 데모)
- 시뮬레이터: `cpcex_hook_simulator.py` (샘플 Excel로 훅 호출 재현)

### 어디에 있나?
- 폴더: `E:\ax\상생\사전 차단\external`
- 실행 방법은 `external\README.md` 참고

### 비개발자 시연 방법(가장 쉬운 방법)
1) 개발자가 서버 실행
2) 참여자는 브라우저에서 `http://127.0.0.1:8000/ui` 접속
3) **샘플 랜덤 로드** → **전송** 눌러 팝업 체험

## 4) PoC-4: 사전 차단 / 내부 호출 방식 (CPCex 내부가 LLM 직접 호출)

### 무엇을 보여주나?
- 외부 훅 서버 없이,
- CPCex 내부(전송 직전)에서 `precheck_mail(payload)`를 호출해
- LLM을 직접 호출하고 Allow/Warn/Block을 결정하는 구조

### 어디에 있나?
- 폴더: `E:\ax\상생\사전 차단\internal`
- 실행 방법은 `internal\README.md` 참고

### 비개발자 시연(웹 UI)
- 개발자가 `internal_ui_server.py` 실행
- 참여자는 `http://127.0.0.1:8001/ui` 접속 후 전송/검사 시연

## 5) 용어 정리(비개발자용)

- **사후 탐지**: 이미 보낸 메일을 나중에 분석해 위험을 찾아냄
- **사전 차단**: 메일을 보내기 전에 검사해 경고/차단/승인으로 막음
- **후보군**: “의심될 가능성 있는 것만” 골라낸 목록(LLM 비용/시간 줄이기)
- **LLM(문맥 기반)**: 문장 의미/의도/상황을 보고 판단하는 AI(예: ChatGPT)
- **근거(evidence)**: 왜 위험하다고 봤는지 보여주는 본문 문장/첨부파일명

## 6) 데모 운영 팁(현장에서 덜 꼬이게)

- UI는 **반드시 서버 URL(/ui)** 로 접속해서 사용하세요.
  - external: `http://127.0.0.1:8000/ui`
  - internal: `http://127.0.0.1:8001/ui`
- `.env`에 `OPENAI_API_KEY`가 반드시 있어야 LLM이 동작합니다.
- 콘솔 한글이 깨지면 파일(JSONL/Excel)로 확인하세요.

## 7) 역할별 체크리스트 (데모/PoC 운영용)

### PM(전하) 체크리스트
- [ ] 오늘 데모에서 "무엇이 성공"인지 한 문장으로 합의(예: Warn/Block 팝업 시연 + 승인 라우팅 표시)
- [ ] PoC 범위 In/Out(실시간 차단 vs 사후 점검, 첨부 내용 분석 불가 등) 명확히 설명
- [ ] 결과를 어떻게 쓸지 정의(검토 우선순위/소명 요청/승인 프로세스 등)
- [ ] KPI 초안 정의(예: Top-N에서 기존 위반 케이스 재발견, 검토시간 절감)

### 실무 담당자(준법/상생 점검) 체크리스트
- [ ] Warn/Block 기준이 업무적으로 납득되는지 피드백
- [ ] false positive(과탐)/false negative(미탐) 사례를 5~10개만 구체적으로 제시
- [ ] "근거(evidence)"가 실제 소명/감사 대응에 충분한지 확인
- [ ] 승인 라우팅(팀준법→사업부준법→부서장) 대상자/역할 정의

### 개발자 체크리스트
- [ ] 실행 전: `.env`의 `OPENAI_API_KEY` 설정 확인
- [ ] 서버 기동 확인
  - external UI: `http://127.0.0.1:8000/ui`
  - internal UI: `http://127.0.0.1:8001/ui`
- [ ] 타임아웃/실패 시 기본정책(warn 권장) 동작 확인
- [ ] 로그/결과 저장 확인
  - JSONL(한 줄 1건) 또는 Excel 결과 파일 생성
- [ ] (운영 대비) 키 관리/마스킹/레이트리밋/캐시 전략 메모

### 데모 진행자(발표/시연) 체크리스트
- [ ] 3개 시나리오를 미리 정해두기
  - Allow 1건 / Warn 1건 / Block 1건
- [ ] UI에서 "샘플 랜덤 로드"로 빠르게 케이스 찾기
- [ ] Block 케이스에서 승인 라우팅(3단계) 표시가 나오는지 확인
- [ ] Warn 케이스에서 "전송 계속(override 로그)" 버튼 설명 준비

### 보안/인프라(있다면) 체크리스트
- [ ] API Key 저장 위치(Secret Manager 등)와 접근 권한
- [ ] 외부 API 호출 허용 정책(방화벽/프록시)
- [ ] 로그에 민감정보(본문/개인정보) 저장 여부와 마스킹 정책
